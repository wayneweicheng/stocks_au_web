# Task 10: Migrate Retained SPX SQLite State to SQL Server

## Objective

Import retained SPX history and immutable HTML from the legacy SQLite database into `StockDB_US.[TradingSignal]` without deleting, overwriting, or re-notifying anything. Produce an auditable, idempotent reconciliation report.

## Prerequisites

- Tasks 02, 04, 06, and 08 are complete.
- The exact production SQLite file has been identified and backed up.
- The target database is an explicitly designated migration/integration database for rehearsal.
- No migration command is run against production without separate user approval.

Store generated reconciliation evidence under a user-approved operational/artifact path, not as temporary database rows only. Never commit production data or report HTML to Git.

## Command contract

Provide:

```text
python -m strategy_runtime.migrations.migrate_spx_sqlite inspect --source PATH
python -m strategy_runtime.migrations.migrate_spx_sqlite dry-run --source PATH --target-environment MIGRATION_SHADOW
python -m strategy_runtime.migrations.migrate_spx_sqlite apply --source PATH --target-environment MIGRATION_SHADOW --confirmation-file PATH
python -m strategy_runtime.migrations.migrate_spx_sqlite verify --source PATH --import-batch-id UUID
```

Requirements:

- `inspect`, `dry-run`, and `verify` never mutate either database.
- `apply` opens SQLite read-only using a URI/read-only mode and verifies its hash has not changed since the confirmation file was created.
- The confirmation file is generated by `dry-run`, records source hash/schema fingerprint/target database and planned counts, and contains no secret.
- Production target Environment requires an additional explicit environment safety flag and user-approved execution; code creation alone does not grant permission to run it.
- Default behavior on an unexpected table/column/version is to stop before writes.

## Source inventory and mapping

Inspect every current table rather than assuming a historical schema. At minimum map:

| SQLite table | SQL Server target |
|---|---|
| `signals` | synthetic/imported `StrategyRun`, `Observation`, and `Signal` |
| `strategy_comparisons` | `StrategyComparison` |
| `trade_plans` | `TradePlan` plus reconstructed `TradePlanEvent` rows |
| `shadow_trades` | the appropriate shadow Execution Book, `TradePlan`, and events |
| `portfolio_state` | deployment-scoped `ExecutionBook` opening/current imported projection |
| `notifications` | `NotificationEvent` and terminal/import-only `NotificationDelivery` evidence |
| `system_events` | `AuditEvent` or lifecycle event when an unambiguous plan relationship exists |
| `strategy_reports` | `ReportSnapshot` plus `ReportAlias` |

Before coding transformations, add a mapping document/test fixture listing every source column, target field, null/default conversion, timezone assumption, and unmapped field. Preserve unmapped legacy detail in namespaced metadata JSON when it has audit value; do not discard it silently.

## Deterministic identity

- Use a fixed documented UUID namespace and UUIDv5 of source database identity, table name, and legacy primary key when a target UUID is required.
- Record every mapping in `LegacyIdentityMap`.
- Preserve a valid legacy opaque report ID as the public report ID when it meets the target constraints and has no collision. Otherwise generate deterministic UUIDv5 and create an alias for every legacy route key.
- Create deterministic imported Strategy Run keys that cannot collide with forward runtime runs.
- Re-running `apply` with the same source produces no duplicate domain rows, reports, events, plans, or queue messages.
- A collision with different content is a terminal migration error, not an update.

## Historical semantics

Imported rows are history, not newly generated actions.

- Mark imported Strategy Runs with migration provenance and their original effective/completed timestamps where available.
- Keep the original Strategy Version and Environment values. Do not relabel legacy production data as newly evaluated production.
- Reconstruct plan events only where timestamps/status unambiguously support them; mark inferred events in metadata.
- If singleton portfolio history cannot reconstruct all intermediate events, preserve the final projection and emit a reconciliation warning rather than inventing trades.
- Imported Notification Deliveries use `SENT`, `FAILED`, `DELIVERY_UNKNOWN`, or `SKIPPED` according to legacy evidence, with `Imported=true` metadata.
- Never insert an imported notification into `[StockDB].[Notification].[MessageQueue]` and never reset it to `PENDING`.

## Reports and legacy links

- Preserve `HtmlContent` exactly, including original encoding after normalizing only the database text representation required by `nvarchar(max)`.
- Calculate and store the actual SHA-256 of imported HTML; compare it with any available legacy hash.
- Preserve original filename, report kind/date, Observation date, Environment, Strategy Version, and generated timestamp.
- Create `ReportAlias` entries for every `spx-gex-report-...html` filename and every exact `<date>.html?report_id=<legacy-id>` identity used by the old FastAPI router. The mutable `/report.html` and date-only URL are resolved by Task 08 queries, not frozen as aliases.
- If two legacy rows claim the same alias, stop and list the collision. Do not route the alias to whichever row is newest.
- Imported reports are immutable; a later correction creates a new snapshot and `SupersedesReportID`, not an update.

## Transaction and restart behavior

- Create one `LegacyImportBatch` before importing and mark it terminal only after verification.
- Import in deterministic dependency-ordered chunks with a transaction per bounded chunk.
- Record checkpoints through committed identity mappings; restart skips exact completed mappings after verifying their content.
- Use a migration-level application lock so two applies cannot process the same source concurrently.
- Roll back a chunk on any mapping/invariant failure.
- Do not delete partially imported valid chunks during recovery; resume or use a separately approved compensating migration.

## Verification report

Generate machine-readable JSON and concise Markdown containing:

- source absolute path, file hash, schema fingerprint, and read-only confirmation;
- counts and min/max timestamps per source table;
- inserted/reused/rejected counts per target entity;
- identity-map completeness;
- report byte/hash matches and alias coverage;
- Signal classification/metrics spot checks;
- Trade Plan status/event reconciliation;
- notification status counts and explicit queue-insert count of zero;
- every warning, inferred mapping, and unmapped source field.

The report must not contain message tokens, connection strings, personal recipient keys, or full production HTML.

## Tests

Create synthetic SQLite fixtures covering all schema versions observed in source initialization/migrations. Cover:

- dry-run performs zero writes;
- apply followed by apply is idempotent;
- changed content under the same legacy identity fails;
- source hash change after confirmation fails;
- unknown column/schema fails closed;
- null/timezone conversions;
- report byte/hash and all alias forms;
- alias collision;
- plan/event reconstruction;
- singleton portfolio limitations reported;
- legacy notifications never enter `MessageQueue`;
- interrupted chunk resumes without duplicates;
- SQLite is opened read-only.

## Acceptance criteria

- All retained source rows are either mapped or explicitly accounted for in the reconciliation report.
- Report HTML hashes and legacy route aliases verify exactly.
- A second migration is a no-op/reuse with no changed target content.
- No source SQLite bytes or rows are modified.
- No imported notification can be sent.
- The original SQLite backup is retained through cutover and rollback retention.

## Out of scope

- Running against production without explicit approval.
- Deleting/compacting SQLite.
- Reclassifying historical Signals with new logic.
- Sending missed historical notifications.
- Repairing ambiguous legacy history by guesswork.
